# The bar behaves the same in every appearance, or it is a defect

**Status:** Audit only. No application code changed on this branch. Read against `origin/main` at `56df55ea` (v0.8.52), where PR #654 has landed and the Escape and window-level fixes have not.
**DRI:** Lacy for the slice order. One agent per slice, named on its issue.
**Verdict:** 25 violations: 13 in the bar (section 2), 12 outside it (section 2b), plus a counted tail. By severity: 8 S1, 11 S2, 6 S3. Eight change what a person meets in ordinary use, and two of those eight are already being fixed (Escape, and the bar's window level).

Two of the seven outrank items 4 and 5 and are not about the bar at all. The agent's three file-editing tools are absent from the risk classifier, so with permission mode set to "ask first" the agent rewrites a file on disk with no prompt. And "is this file path allowed" has three implementations, the weakest of which guards the seven command entry points the system agent actually calls, with no workspace root and no credential blocklist.

Inside the bar the worst is not Escape, it is hover. Rust installs a mouse tracking area on the bar window and emits enter, move and leave for every appearance, and only the Pill listens. The other seven read raw DOM pointer events instead, which the Pill's own source calls "the flicker".

## The ask

Lacy, 2026-10-01: "Based on items 4 and 5, I think we need to do a full audit to make sure that behavior is written in rust and not in the UI, so it's not per appearance or per call site. It is uniform and works in every appearance always exactly the same."

Items 4 and 5 were the floating bar covering the settings window, and Escape not always collapsing the bar back to idle.

## 1. The rule, in one sentence

Rust decides, React draws; a behavior has exactly one owner, and every appearance reaches it by calling the same thing rather than by containing a copy of it.

A violation is any of these:

- The same decision is written out in more than one appearance or more than one call site. Eight copies that agree today are still a violation, because the ninth will not.
- A shared function is correct only when every caller remembers to wrap it, guard it, or call something else first.
- A control, setting, constant or function names a behavior it is not connected to. This is the **dead control pattern**, already named in this project: gravity wells in one of eight looks, Escape in seven differently-named local states, the bar's window level with four owners, `format_task_output` fixed per call site, and a third allowlist that decided nothing. Rows 1, 9, 10 and 12 below are four more.
- A `useEffect` enforces a policy rather than reflecting state Rust already holds.

Not a violation: two appearances drawing the same state differently on purpose. The Orb is colour and the Avatar is a face. That is the product, and section 6 says where that applies.

## 5. The mechanism that stops the ninth appearance

Four candidates, judged on whether they would have caught the thirteen rows above.

**A Rust trait or enum that makes an unhandled state a compile error.** Would not have caught one row. The behavior is in React, and Rust cannot compile-error a missing React hook call. Rust does not even have an appearance enum today: `src-tauri/src/constants/ui.rs:44-63` is a module of `&str` constants, so there is nothing to match exhaustively. Building the enum is worth doing for other reasons and buys nothing here. **Do not build this as the mechanism.**

**A shared TypeScript type where a missing field is a type error.** This is what slices 1, 2 and 4 produce: one hook per behavior with a typed return. It makes the single owner exist, which is necessary. It is not the guard, because TypeScript cannot require that a new component call a hook. An appearance that simply does not call `useBarHover` type-checks perfectly and has no hover. **Build it, as the thing the guard tests, not as the guard.**

**`satisfies Record<BarState, …>` over a generated `BarState` union.** There is no `BarState` type in the frontend at all today; states are bare strings and every appearance's mapper ends in a `default:` that quietly means idle. Generate `BarState` as a union from `src-tauri/src/constants/ui.rs:67-85` into `src/lib/constants.generated.ts`, then annotate each appearance's state map with `satisfies Record<BarState, …>`. A new Rust state then becomes eight type errors instead of eight silent fallbacks. Cost: a generator change plus eight annotations, roughly half a day. It closes a real hole and it is cheap. **Build it, second.**

**A conformance test that enumerates the appearance catalog.** This is the one I would actually build, and it is first. For each of the eight entries in `src/components/bar/appearanceCatalog.ts`, mount the real component through `BarHost` on the existing harness shim and assert every behavior in one table: the native hover events are honoured and a verified leave is not believed; the launch sequence is `set_bar_frame` then `show_bar_when_ready` and the dock slot is seeded; Escape from each open state returns to idle and arms the Rust monitor; the resize ordering and the Reduce Motion delay; the dismiss duration matches the shared policy. One file, roughly 300 lines, maybe a day.

It is the only candidate that fails for an appearance which forgot to call the shell, which is the actual failure mode in every row above. Four precedents in this repo already work this way: `src/components/bar/__tests__/appearanceMigration.test.tsx:75` asserts over the whole catalog; `src-tauri/src/commands/settings.rs:683` holds a Rust allowlist against a struct and its own comment says "nothing but this test stops them drifting"; `src-tauri/src/constants/agent.rs:30-34` says `tool_config` "has a test that fails if these two lists drift apart" for the browser tool names, which is exactly the test W1 shows was never written for the file tools; and `src/bar-harness/barHarnessTauri.ts` already fakes every Tauri call the bar makes, so the hard part is built.

The pattern across all four is worth naming, because it is the generalisation: **when one list has to match another list, a test that enumerates one and asserts against the other is the cheapest guard this codebase has, and it works every time it is written.** Three were written. The fourth, the one for the file tools, was not, and W1 is the result. Section 2b's twelve rows are twelve more lists that nothing holds against each other.

Where it goes: `src/components/bar/__tests__/appearanceConformance.test.tsx`. It must iterate `APPEARANCE_CATALOG` rather than list eight names, so adding the ninth entry to the catalog adds nine failing assertions on the same commit. Each slice above adds its row to this one table; by slice 7 the table is the specification.

**Recommendation: the conformance test first, the generated `BarState` union second, the shared hooks as the thing they test, and no Rust appearance enum.** Total about a day and a half of agent time, and it runs inside the 24 seconds the bar suite already costs.

For section 2b, the same mechanism in its cheapest form: one list-against-list test per slice, written in the slice that fixes the row. Slice A's is the highest-value single test in this document, because the thing it pins is a permission gate. Do not try to build one mechanism that covers both the bar and the rest of the app; the bar has a catalog to enumerate and the rest does not.

One thing to copy from elsewhere in the codebase while doing it: `follow_cursor_display` is how this is supposed to look. The setting is read in Rust (`src-tauri/src/commands/settings.rs:250`), Rust stops emitting the event (`src-tauri/src/platform/cursor_follow.rs:105`), and no appearance contains a check. Turn the setting off and it is off everywhere, in all eight looks, with zero React code involved. That is the target shape for every row in section 2.

- **State coverage.** I expected gaps and found none. All seventeen Rust bar states are referenced in all eight appearance models (`narratorModel.ts`, `studioModel.ts`, `islandModel.ts`, `shaderOrbModel.ts`, `orbModel.ts`, `haloModel.ts`, `avatarModel.ts`, `FloatingBar.tsx`). - **Cmd+Enter.** Seven copies, all identical, all pure forwarders to a Rust handler that already guards empty input (`src-tauri/src/commands/ui_commands.rs:1334-1340`). It would ride along in slices 1 through 4 for free and does not justify a slice. Listed under cosmetic, not in the table.

- **Every duplicated constant in the Rust backend.** I expected to find a threshold defined twice with two different values and found none: the duplicates all currently agree (`src-tauri/src/commands/export.rs:108` and `src-tauri/src/commands/conversation_history.rs:30` are both 60 under two names; the bar-config defaults have four copies that match). `src-tauri/src/commands/debug_utils.rs:336-351` even holds a test written because a hold-key cap once was duplicated with different values.
